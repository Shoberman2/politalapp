## Problem Statement

BallotWatch has four months of product depth (bill alerts, iOS app, historical chamber,
finance, forecast foundation) and no distribution. The user asked for four things:

1. An audit of the platform.
2. A way to get more users.
3. A way to become the place AI agents go for congressional data.
4. Edits to the landing page.

And one product idea to evaluate: an AI agent that represents a user and speaks to their
representative's office on their behalf.

The unifying diagnosis: every page that carries the actual record (556 members, 1,547 roll
calls, 182,642 bills, 373,041 member votes) is invisible to search engines and to AI crawlers,
and the API that could serve agents is behind a $50 to $500 per month key while the same data is
readable for free through the public Supabase anon key. The product is built. The doors are shut.

## Audit Findings

Verified on 2026-09-05 against the live site (www.ballotwatch.io), the repo at ad26060, and the
production Supabase project.

### Discoverability (blocking)

- Any non-JavaScript client (curl, GPTBot, ClaudeBot, PerplexityBot, most link unfurlers) gets the
  identical 5,262-byte SPA shell for `/`, `/politician/P000197`, and every bill page. Zero record
  content is served as HTML. Google renders JavaScript slowly and ranks such pages poorly; most AI
  crawlers do not execute JavaScript at all.
- `public/robots.txt` points `Sitemap:` at `politicalapp.vercel.app`, not `www.ballotwatch.io`.
  `public/sitemap.xml` lists 26 URLs, all on the wrong domain, with `lastmod` 2026-03-01. No
  member, bill, or roll-call URL is in it. The `politicalapp.vercel.app` host still serves the
  full site with no redirect, so two indexable copies exist.
- `/llms.txt` returns 404. The OpenAPI spec exists at `docs/api/openapi.yaml` but is not served at
  any public URL (`/openapi.yaml` and `/docs/api/openapi.yaml` both 404).
- The April 2026 CEO plan (`docs/designs/go-to-place-accountability.md`) called per-vote SEO
  pages "THE wedge." The Wave 1 plan locked a Next.js migration. Only the schema and slug
  foundation shipped (PR #2). No `/vote/...` route exists in `src/App.jsx`. The migration decision
  blocked the wedge for four months while feature work continued.

### API and data access (contradictory)

- `GET /api/v1/*` returns 401 without a `bw_live_` key. Keys require an active subscription
  ($50, $200, $500 per month in `src/components/DeveloperPortal.jsx`).
- The Supabase anon key (embedded in the bundle, and already public via `TODOS.md`) reads
  `politicians`, `votes`, `roll_calls`, and `bills` with no auth. Row counts via anon HEAD requests:
  politicians 556, votes 373,041, roll_calls 1,547, bills 182,642.
- Net effect: the paid API guards data that is free one layer down, and agents cannot discover
  either path. Nobody pays, nobody scrapes, nobody cites.

### Auth and pricing (dead code in production)

- The route guard is a pass-through; the auth and subscription checks are
  commented out. Every "protected" route is public. `/pricing` sells a monthly plan that gates
  nothing. Stripe checkout and webhook code exist.
- A second, real guard gates only `/alerts`.
- (Both guards have since been replaced by `src/components/AccessGate.jsx`, driven by the list
  in `shared/access.js`.)

### Data quality visible to the public

- `https://www.ballotwatch.io/s/bill/119/hr/1` (the social share card) titles the page as the
  reconciliation act but the meta description begins "The For the People Act of 2025 is a piece of
  legislation aimed at..." `api/_lib/billCard.js` takes the first paragraph of the
  `bill_explanations` row, so this is a wrong row or a wrong key for the most-searched bill of
  the Congress, served to every link unfurler. The render took 4.5 seconds.
- Known from earlier sessions and still open: placeholder bill titles, corrupt or missing
  `roll_call_stats`, and the Montana at-large bug in `src/services/district.js`. Mass indexing
  before these are gated would put bad records in front of Google and every agent.

### Health

- Unit tests: 82 files, 515 tests, all passing (33.5 s).
- Build output: one 1,009 KB JavaScript chunk and a 199 KB stylesheet. No route-level code
  splitting. Landing media: three clips (`hero-run.mp4` and `hero-topdown.mp4` in the opening
  film, `hero-bill.mp4` in the `.voting` section) plus posters, about 2.7 MB. Fonts load from
  three origins. A ZIP-lookup landing page should not need 1 MB of JavaScript before first
  interaction.
- Engagement instrumentation: Vercel Analytics is wired; numbers were not readable from this
  session. `ai_sessions` has 0 rows (the AI Congress simulation has never run in production).
  GitHub: public repo, 0 stars, 0 forks, empty description.
- Operational gaps carried in `TODOS.md` as High: Google sign-in not configured, Gmail briefing
  delivery not configured. Bill-alert email delivery is off by flag. The retention loops are
  half-on.

## Demand Evidence

What exists:

- Product Hunt launch assets in `marketing/product-hunt/` and a landing film mean a launch
  happened or was prepared. No traffic, signup, or retention numbers were available in the repo.
- Prior user feedback recorded in memory: the marketing-style landing read as "very AI"; the user
  wanted real votes shown, not a pitch. That is a taste signal, not a demand signal.
- Zero external signals found: 0 GitHub stars, 0 AI Congress sessions, no API organizations
  visible.

What is missing, and only the founder can supply: weekly visitors, top referrers, indexed page
count in Google Search Console, top search queries, ZIP lookups per visit, alert signups. Every
recommendation below is a bet against those numbers. See The Assignment.

## Status Quo (what the target users do today)

- **A voter who wants "how did my rep vote on X"** searches Google, lands on GovTrack (dated but
  indexed for every vote since 1789) or Congress.gov (official, unreadable), or gives up and asks
  ChatGPT, which cites whichever site served it HTML.
- **An AI agent or an LLM with browsing** asked the same question fetches GovTrack, Congress.gov,
  or Wikipedia. It never fetches BallotWatch because BallotWatch serves it an empty div.
- **A developer building a civic app** uses the Congress.gov API directly (free, no rate limits,
  awkward shapes) or GovTrack's bulk data. BallotWatch's cleaner shapes are behind a paywall they
  will not cross for data they can get free.
- **A constituent who wants to contact their rep** uses 5 Calls (phone scripts), Resistbot (text
  to fax/CWC), Democracy.io (EFF, web-form automation that has decayed as offices moved to
  CWC-only intake), or the member's own web form.

## Target User and Narrowest Wedge

Target human: the person who just heard "the House passed X" and wants to know how their
representative voted, in the next 30 seconds, from a phone. Secondary: the agent acting for that
person (ChatGPT, Claude, Perplexity, a home-grown MCP client) that needs a citeable, structured
answer.

Narrowest wedge that creates users this month: every member page and every roll-call page served
as real HTML with the tally, the member's vote, the source link, and JSON-LD, plus a sitemap that
lists all of them, plus `llms.txt` and an unauthenticated JSON API. No migration. No new product.

## Constraints

- React 18 + Vite SPA on Vercel with Supabase. Keep it. The Next.js migration is explicitly
  rejected in this design (see Premises).
- `DESIGN.md` governs all UI: editorial broadsheet, Instrument Serif, warm paper, restrained
  color, no dashboard gauges.
- `AGENTS.md`: no public forecast UI until the provenance audit reports GO.
- Public data only. Upstream is U.S. government public domain; BallotWatch-derived fields need an
  explicit license (Open Question 6).
- Solo builder. Anything that needs a weeks-long external approval (House CWC vendor status)
  starts now and ships later.
- Political positions are sensitive personal data. Anything storing a user's stances must be
  encrypted at rest, deletable, and never used for anything but the user's own messages.
- Vercel Firewall rate limiting is plan-gated; this design does not assume it. Per-IP limits use
  an Upstash Redis counter (one new dependency, one new secret).

## Landscape

Layer 1 (known): GovTrack owns the archival long tail. Congress.gov is the source of truth.
Quorum and FiscalNote own paid advocacy tooling. 5 Calls and Resistbot own consumer contact.
Layer 2 (current discourse, searched 2026-09-05): `llms.txt` is a community convention, adopted by
roughly 10 percent of measured domains and by Stripe, Cloudflare, Vercel, and Anthropic; its real
use is as a routing layer for agents. Sites serving Markdown instead of HTML report up to 10x
token reductions. House offices accept vendor-delivered constituent mail only through the
Communicating with Congress (CWC) API, which requires a CAO vendor application, a level-of-service
agreement, and a strict XML format with address-verified constituents. Congressional staff are
already using AI to triage constituent mail. A House member requested funding in July 2026 for an
in-office AI assistant. Senator Warner's AI AGENT Act of 2026 (S.5051) would let people bring
their own agent to any platform, a tailwind for agents that act on behalf of users.
Layer 3 (where conventional wisdom is wrong here): the April plan assumed the SEO wedge required
a framework migration to get ISR and server components. It did not. The repo already has a
working server-rendered HTML endpoint (`api/share.js`) that reads Supabase and returns a full page
with cache headers. The same pattern, applied to member and roll-call URLs, is the wedge. The
"correct" architecture was the thing that prevented shipping.

EUREKA: Everyone migrates to Next.js for SEO because they assume crawlable pages need a
server-rendering framework. But `api/share.js` already proves a Vercel function can render a
cached content page from Supabase in one file. This means the wedge is a rewrite rule and one
function, not a migration.

## Premises

1. Distribution, not features, is the constraint. Phases 1 to 3 (crawlable record, agent front
   door, record-first landing) ship before any new product surface. "Tell your rep" is the only
   new surface in scope and comes last, in week 5 or later.
2. Bots and humans both receive the record as HTML from a Vercel function on member, bill, and
   roll-call URLs. There is no user-agent split. React then replaces the server markup on the
   client (replace, not hydrate).
3. The Next.js migration stays rejected. Server-rendered content pages are delivered by Vercel
   functions using the existing `api/share.js` pattern.
4. The data is public. Make free access intentional: unauthenticated GET on the API with per-IP
   limits and attribution, and keys (free, self-serve) for higher limits. Paid tiers are an open
   question, not a Phase 2 deliverable.
5. Being "a spot for AI agents" means being cited and being wired in, not being scraped. The
   mechanisms are HTML with JSON-LD, `llms.txt`, a public OpenAPI URL, Markdown by content
   negotiation, and an MCP server listed in registries.
6. Bad records do not get indexed. Any page failing a data-quality gate returns `noindex` and is
   excluded from the sitemap until the record is fixed.
7. The landing page leads with the record (today's vote, real numbers, ZIP box in the first
   screen), not a film. This restates the user's own prior feedback ("very AI"; show real votes).
8. The AI representative idea is real and is last in sequence. Its hard part is delivery, not
   drafting. Nothing sends without a human approving and signing; no autonomous phone calls to
   congressional offices.

## Approaches Considered

### Approach A: Open the doors (minimal, recommended)

Summary: fix crawlability with one prerender function and rewrites, publish `llms.txt` and the
OpenAPI spec, open unauthenticated GET on the API, ship an MCP server, and rework the landing page
to lead with the record. Then ship "Tell your rep" as a button, not an agent.
Effort: M (Phases 1 to 3: human about 4 weeks / CC about 5 working days; Phase 4 in week 5 or later, CC 1 to 2 days)
Risk: Low
Pros: ships in days; no migration; reuses `api/share.js`, `api/_lib/billCard.js`, `api/v1/*`,
`SEO.jsx`, `api/og.jsx`; creates measurable signal (indexed pages, referrers) within weeks.
Cons: two render paths (function HTML first, React replacing it) must stay in sync on titles and
canonical URLs; per-IP rate limiting adds Upstash; the prerender function must be bounded so
crawlers cannot fan out 182,642 uncached bill queries.
Reuses: `api/share.js`, `api/_lib/billCard.js`, `api/_lib/supabase.js`, `api/v1/*`,
`docs/api/openapi.yaml`, `src/components/SEO.jsx`, `api/og.jsx`, and the slug and lock
primitives from `supabase/migrations/003_seo_pages_and_lock_primitives.sql`. Note:
`get_vote_page_data(slug)` from that migration returns one member's vote and is not reused for
roll-call pages; two new RPCs are specified in Phase 1.

### Approach B: Finish the April plan (ideal architecture)

Summary: execute the Wave 1 Next.js App Router migration with ISR, then build the agent surface
and the AI representative on top.
Effort: XL (human: 6 to 8 weeks / CC: 1 to 2 weeks plus QA of every route)
Risk: High
Pros: one render path; native ISR and revalidation tags; the design review and mockups already
exist in `docs/designs/wave-1-seo-wedge.md`.
Cons: it has already failed to ship for four months; it touches every route, the iOS app's
assumptions, and Playwright suites; nothing user-visible lands until the migration is complete.
Reuses: the Wave 1 plan and mockups.

### Approach C: Agent-first (lateral)

Summary: treat the API, MCP server, Markdown responses, and bulk snapshots as the primary product.
The website becomes a rendered view of the API. The landing page is the front door for both a
person with a ZIP code and an agent with a query.
Effort: L (human: 4 to 5 weeks / CC: 3 to 4 days)
Risk: Medium
Pros: aligns with where discovery is moving; makes citation the growth loop; the API already
exists.
Cons: most people still arrive from Google; an API-shaped landing page loses the editorial
identity in `DESIGN.md`; harder to measure early.
Reuses: everything in A plus the developer portal.

### Approach D (ruled out): AI representative first

Ruled out because delivery requires House CWC vendor approval (months) and because without
Approach A nobody arrives to use it.

## Recommended Approach

Approach A, with two items pulled forward from C: the MCP server (it is the only mechanism that
makes agents wire BallotWatch in by name) and Markdown responses for member and roll-call pages.

### Phase 1: Crawlable record (CC: about 2 days)

1. **Canonical host.** Add a host-conditional 308 in `vercel.json` so `politicalapp.vercel.app`
   (and its `-git-main` alias if present) redirects to `https://www.ballotwatch.io` for every
   path. Leave preview deployments alone: Vercel already sends `X-Robots-Tag: noindex` on them
   and Playwright and preview QA depend on them.
2. **Routes.** Keep `/politician/:bioguideId` and `/bill/:congress/:type/:number`. Add
   `/vote/:congress/:chamber/:session/:roll` (House and Senate roll numbers reset each session;
   2026 is session 2 of the 119th, so session is part of the key). The route resolves to
   `roll_call_id` in the form `house-119-2-123`.
3. **Prerender function `api/prerender.js`.** For those three shapes it returns a full HTML
   document: title, description, canonical on `www.ballotwatch.io`, Open Graph, JSON-LD
   (`Person` with `sameAs` to bioguide and congress.gov; `Legislation`; `BreadcrumbList`; no
   ranking expectation from `Legislation` or `VoteAction`, they are for machine readers), and the
   record in semantic HTML inside `<div id="root">`, including the app chrome (`.app`, the
   masthead markup from `Navigation`, `main.main-content`) and the loaded-state class names
   from `PoliticianDetail.jsx` (`pol-*`) and `BillDetail.jsx`, so the client swap is
   content-to-content. Script and stylesheet tags come from fetching `${origin}/index.html` at
   runtime (cached in-function for 5 minutes) because asset names are hashed per deploy and
   `dist/` is not bundled into functions. `src/main.jsx` keeps `createRoot().render()`:
   replace, not hydrate. Accept one re-render. Error path: on any exception or a 3 s data
   timeout, return the cached `index.html` unchanged with `Cache-Control: no-store` and log the
   error, so a Supabase hiccup degrades to today's SPA shell rather than a text error. Set
   `maxDuration` to 10 s.
4. **Data.** Two new RPCs, granted to anon: `get_member_page(bioguide_id)` (member, terms,
   stats, last 50 votes with bill title and source URL) and `get_roll_call_page(roll_call_id)`
   (roll call, tally, bill, every member's vote). "Result" is not stored: `roll_calls` has no
   result column and the client derives it in `deriveResult()` in `src/services/floorVotes.js`
   (two-thirds threshold for suspension questions, tie handling). Port that rule into the RPC
   (or a shared `api/_lib/rollCallResult.js` used by prerender, Markdown, and the API) and
   label the field `result_derived`. "Tally" is yea plus nay from `roll_call_stats`. Bill pages
   reuse `fetchCardData` from `api/_lib/billCard.js`. `data_updated_at` everywhere is the
   `etl_metadata` row with key `last_successful_run`.
5. **Bounding.** Members and roll calls are always prerendered (about 2,100 pages). Bills are
   prerendered only when they have a recorded vote or a CRS summary; every other bill URL falls
   through to the SPA with `Cache-Control: public, s-maxage=300`. This caps crawler fan-out.
6. **Cache.** `Cache-Control: public, s-maxage=900, stale-while-revalidate=86400`. No purge
   mechanism in version one; the ETL runs in GitHub Actions without a Vercel token, so a
   15-minute edge TTL with a day of stale-while-revalidate is the whole freshness story. Add
   `Cache-Tag` and the Vercel purge API later if 15 minutes proves too slow.
7. **Data-quality gate, evaluated nightly by the ETL, not per request.** A new ETL step writes
   `indexable boolean` on `politicians`, `roll_calls`, and `bills` (or a `page_index_status`
   table keyed by page id). Prerender reads the flag to decide `<meta name="robots"
   content="noindex">`; the sitemap reads only `indexable = true` rows. Rules:
   - Bill title is a placeholder: title is null, or matches
     `^(H\.?R\.?|S\.?|H\.?J\.?Res\.?|S\.?J\.?Res\.?|H\.?Con\.?Res\.?|S\.?Con\.?Res\.?|H\.?Res\.?|S\.?Res\.?)\s*\d+$`
     (the stub form `floorVotes.js` already documents). Reuse the same rule in ETL, prerender,
     and sitemap.
   - Roll call: yea plus nay in `roll_call_stats` does not equal the count of `votes` rows with
     position in ('Yea', 'Nay') for that `roll_call_id`.
   - Member: zero rows in `votes` (nothing to show yet). Former members with votes stay
     indexable.
   - Bill one-liner names an act absent from the official title, short title, and CRS summary.
     Act-name extraction: the first match of
     `\b(?!(?:This|The|That|An|Such)\s+Act\b)([A-Z][\w'’]+(?:\s+[A-Za-z][\w'’]+){0,7}\s+Act(?:\s+of\s+\d{4})?)`
     in the one-liner, compared case-insensitively; the negative lookahead keeps
     "This Act amends..." from tripping the gate.
8. **H.R. 1 root cause.** Inspect the `bill_explanations` row for `119-hr-1` and the key used by
   `fetchCardData`; correct the row; the gate above prevents recurrence.
9. **Canonicals.** `api/share.js` sets canonical to `/bill/:congress/:type/:number` and adds
   `noindex`; `/s/bill/*` remains the social card only.
10. **Sitemap.** Delete `public/sitemap.xml` (static files are served before rewrites). Add
    `api/sitemap.js` serving a sitemap index on the canonical domain that points at
    `sitemap-members.xml`, `sitemap-votes.xml`, and `sitemap-bills-N.xml` (50,000 URLs per part),
    each built from `indexable = true` rows using paginated service-role queries (PostgREST caps
    anon responses at 1,000 rows). `lastmod` uses `roll_calls.voted_at` for votes, the latest
    action date for bills, and the latest vote date for members; do not use `updated_at`, which
    the ETL trigger bumps on every touch. `Cache-Control: public, s-maxage=3600`. Fix
    `robots.txt` to point at the index and to explicitly allow GPTBot, ClaudeBot,
    Claude-SearchBot, PerplexityBot, Google-Extended, Applebot-Extended, and CCBot (Open
    Question 2).
11. **`vercel.json` rewrites**, in this order and ahead of the SPA catch-all:

    ```json
    { "source": "/politician/:bioguideId", "destination": "/api/prerender?kind=member&id=:bioguideId" },
    { "source": "/bill/:congress/:type/:number", "destination": "/api/prerender?kind=bill&congress=:congress&type=:type&number=:number" },
    { "source": "/vote/:congress/:chamber/:session/:roll", "destination": "/api/prerender?kind=vote&congress=:congress&chamber=:chamber&session=:session&roll=:roll" },
    { "source": "/sitemap.xml", "destination": "/api/sitemap" },
    { "source": "/sitemap-:part.xml", "destination": "/api/sitemap?part=:part" }
    ```

### Phase 2: Agent front door (CC: about 2 days)

1. **`/llms.txt`** (static, in `public/`): what the site is, canonical URL patterns for members,
   bills, and roll calls, the API base and `/openapi.yaml`, the MCP endpoint, freshness (daily
   ETL), sources, and citation format.
2. **OpenAPI at a public URL.** Copy `docs/api/openapi.yaml` to `public/openapi.yaml` at build
   (`prebuild` script) and link it from `llms.txt` and `/developers/docs`.
3. **Unauthenticated GET on `/api/v1/*`.** In `api/_lib/auth.js`, a request without a bearer
   token is allowed for GET with a per-IP sliding window in Upstash Redis: 60 per minute and
   5,000 per day to start. `validateApiKey` returns `{ key: { id: null }, ipHash }` for
   anonymous requests, `logUsage` takes `{ keyId, ipHash, endpoint, method, status, ms }`, and
   `api_usage.key_id` becomes nullable with a new `ip_hash` column (SHA-256 of IP plus a server
   salt); every v1 handler's `logUsage` call is updated. Anonymous responses carry
   `Cache-Control: public, s-maxage=300, stale-while-revalidate=3600` (no `Authorization`
   header, so the CDN can cache them); keyed responses stay uncached. Because agent platforms
   share egress IPs, self-serve free keys get 600 per minute: a "Get a free key" action on
   `/developers/keys` creates an organization with `plan = 'free'` and
   `subscription_status = 'active'` with no Stripe step, and `auth.js` maps `plan = 'free'` to
   that tier. This is what `llms.txt` tells agents to use. Every response carries
   `data_updated_at` and, for single records, `Link: <source_url>; rel="canonical"`. Paid
   tiers and the pricing UI are untouched in this phase (Open Question 5).
4. **Markdown by content negotiation.** `Accept: text/markdown` on member, roll-call, and bill
   URLs returns Markdown from the same RPCs. No `.md` suffix (the SPA catch-all excludes dotted
   paths and a suffix would need its own rewrites). Fields: member (name, party, state, district,
   chamber, terms, source URL, last 50 votes as a table of date, roll call, question, bill,
   vote, result); roll call (chamber, congress, session, roll, date, question, bill, result,
   tally, a table of every member and vote); bill (number, title, sponsor, latest action,
   CRS summary, recorded votes, source URL).
5. **MCP server `api/mcp.js`**, stateless Streamable HTTP on the Node runtime (no SSE session
   store, no Redis; `sessionIdGenerator: undefined` or Vercel's `mcp-handler` without Redis),
   with tools `find_representatives(address | zip)`, `get_member(bioguide_id)`,
   `get_member_votes(bioguide_id, since?, limit?)`, `get_roll_call(congress, chamber, session,
   roll)`, `search_bills(query)`, `get_bill(id)`, and `explain_bill(id)` (returns the cached
   official CRS-based explanation only; never triggers generation on an anonymous request).
   Bill ids use the existing `119-hr-1` form. `find_representatives` runs the Census geocoder
   server-side for street addresses; for ZIPs it uses the HUD USPS ZIP-to-congressional-district
   crosswalk, shipped as a static JSON under `public/data/`, and returns every district a ZIP
   touches rather than guessing. The Montana at-large bug in `src/services/district.js` (MT has
   had two districts since 2023) is fixed here and in the landing ZIP lookup before this ships.
   Every result carries `source_url` and `data_updated_at`. Listings: the official MCP registry,
   Smithery, and Glama are self-serve; the Anthropic connector directory requires partner
   review, so apply and wait.
6. Deferred to Phase 5: `/llms-full.txt`, `Dataset` JSON-LD for Google Dataset Search, gzipped
   bulk snapshots under `/data/latest/`, and the license decision.

   measure first: run `vite build` with a bundle report, then target the landing chunk under
   250 KB gzipped and LCP under 2.5 s on mobile. If splitting alone misses the target, defer
   the supabase and axios imports on the landing until the first ZIP lookup or feed render.

### Phase 4: "Tell your rep" (week 5 or later, CC: 1 to 2 days)

The strongest version of the idea: a lobbyist for people who cannot afford one. The agent knows
the user's positions, watches for relevant votes, drafts a message in the user's voice that cites
the exact roll call and the member's own record, the user approves with one tap, it is delivered
through a channel offices count, and the user later sees "your representative voted against your
stated position three times since you wrote."

What is true about the hard parts:

- Delivery is the moat and the blocker. House offices accept vendor mail only through the CWC
  API (vendor application via the House CWC page, level-of-service agreement, XML standard,
  district determined from a verified mailing address). The Senate runs a parallel
  vendor-delivery program. Reverse-engineered web forms decay and are treated as spam. An AI
  placing voice calls to a congressional office "on behalf of" a constituent would be logged as
  spam at best and a news story at worst. Do not build that.
- Authenticity is the value, and generic AI text destroys it. Offices already discount form
  letters and now use AI to triage mail. What a staffer cannot dismiss is a message from a
  Census-verified constituent that cites a specific roll call and the member's own record. That
  is exactly what BallotWatch has and nobody else does.
- Rules that make it defensible: every message is user-edited and user-signed; nothing sends
  autonomously; verified address required before anything is counted; per-user rate limits;
  positions stored encrypted and deletable; disclosure that drafting assistance was used if an
  office asks. Individual constituents petitioning their own members is not lobbying under the
  Lobbying Disclosure Act, and there is no TCPA exposure when the human sends. Confirm both with
  counsel before launch; they are stated here as working assumptions.

The wedge that ships without vendor approval: a "Tell your rep" button on every roll-call and
member page. It opens a draft addressed to the member, prefilled with the roll call, the vote,
the source link, and the user's district. District comes from the saved address
(`saveUserAddress` in `src/services/userService.js`; account-backed when signed in, otherwise
local). The user edits, then sends by the official contact form or by copy. The form URL is
a new `politicians.contact_url` column, populated by the ETL from the Congress.gov member
`officialWebsiteUrl` plus `/contact`, with a small hand-curated override table for offices
whose form lives elsewhere; a member with no resolvable URL shows the office phone number
instead. Counting:
"drafts opened" is counted for everyone; "sent" is counted only for signed-in users with a
verified address who confirm after sending, and is shown publicly only once CWC delivery exists
and the number is verifiable. Until then the public label is "N constituents drafted a message
about this vote." That count is the demand evidence that supports the CWC vendor application,
which should be filed now because approval is the long pole.

After CWC approval: the same button delivers through CWC with address verification, and
"positions" (a short list of issues the user cares about) turns alerts into drafts
automatically, still one tap to approve.
